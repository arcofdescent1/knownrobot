# KnownRobot reproducibility release candidate

## Scope and source

The candidate brings native identity/navigation and gaps 1–4 into one repository
release: connected policy revisions, local measured evaluation, shared portable
manifest gates, evidence-linked compatibility answers and honest community proof.
Production deployment and database application are separate, deferred actions.
Do not describe this candidate as live merely because its tests pass.

The approved production branch remains `main`; work is prepared on a `codex/`
release branch. Merge only after Registry release checks, Verification
authorization, Validator, Measured simulator evaluation and applicable Sprint
commitments checks pass. Do not deploy an uncommitted local directory.

`npm run build` generates an ignored build-time receipt. `npm run release:check`
requires a clean source checkout, synchronized contracts and a receipt matching
the current commit and source tree. `/release.json` exposes the bundled receipt
without credentials. Compare its revision and source digest to the approved
checkout after eventual deployment. A dirty or absent receipt is not an approved
release. This is not a cryptographically signed supply-chain attestation.
Text digests normalize CRLF to LF so approved Windows and Linux checkouts can
be compared. Source uploads without `.git` remain buildable, but their receipt
explicitly reports unknown cleanliness and application-only snapshot scope;
they cannot pass the clean-Git release gate. A Vercel-provided commit value is
reported as a declared revision, not proof of an unchanged checkout.

## Community completion gate

`npm run sprint:proof` exits nonzero while real measured community proof is absent.
That is a business/evidence gate, not a reason to fabricate seed data or prevent
shipping an honest recruiting utility. `/sprints/status.json` distinguishes
operating readiness, every recorded outcome and measured community proof.

The first sprint still needs a confirmed event lead, two independent reviewers
and three to five actual teams. At least three teams must submit reviewed measured
trials, including two physical-hardware teams for this physical-transfer study.
Obtain pre-trial configuration/protocol commitments, keep every blocked/unsafe/
failed/withdrawn outcome, hold the public session and publish the signed joint
report with credits, corrections and improvement issues. All-measured failures
can establish a measured community loop; they cannot establish successful transfer.
Closing an improvement issue does not mean the associated fix was independently
verified. Distinct handles alone do not prove organizational independence.

Use the existing application/evidence/review issue forms and
`community/sprints/README.md`. Run `npm run sprint:verify` to authenticate public
comment author, exact consent token, revision-bound snapshots and transitions.
Do not appoint people, send invitations or start robot execution without their
real commitments. If readiness is unmet by kickoff, the actual lead must postpone
and renew consent; dates never auto-start or auto-complete the sprint.

## Compatibility answers

Each real evidence page and its `compatibility.json?page=N` endpoint answer for
that exact canonical policy, declared hardware and protocol on the current page.
They expose coverage, per-record rates, failures, completeness and review strength.
Known simulation and physical execution are separated; unspecified execution,
missing protocol fields and incomplete manifests are not comparable declarations.
Percentages and counts are never pooled or reconstructed. Review-backed records
do not turn distinct accounts into proven independent teams or certify safety.

## Release verification

Run web tests, lint, production build, production/preview smoke tests and the
installed-wheel test. Run Python with the actual evaluation extras and
`KNOWNROBOT_REQUIRE_SIM_TESTS=1`; do not count skipped simulations as execution
verification. Run `supabase/tests/run_verification.py` on a disposable PostgreSQL
17 cluster only. CI runs those checks without production secrets. Then commit the
approved source and regenerate/check the receipt from the clean checkout.

Deployment drift remains open until the eventual approved release is deployed
and its live receipt, schema history, identity session and evidence workflows are
verified. No production branch protections, repository push, deployment or human
participation is implied by this candidate.
